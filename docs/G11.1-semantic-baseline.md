# G11.1 — Semantic Baseline

Status: **DRAFT — NOT FROZEN**

## Purpose

Define the semantic claim and independent oracle for G11 before any G11 tests or implementation changes are designed.

G10 established technical/implementation validation of the isolated branch. G11 must establish a stronger proposition: that the implementation's observable behavior conforms to an independently stated semantic contract.

## Source-of-truth boundary

The semantic baseline is derived from the design-level contract documented in `README.md` and the stated Evolution Application Contract v1.0 semantics. It is **not** derived from the current Rust control flow, current test assertions, current error variants, or current helper structure.

The current implementation is evidence to be checked against the baseline, not an authority for defining it.

## Candidate Claim

> **G11 Claim C1 — Evolution-plan application preserves the contract's state-transition semantics:** for every plan admitted by the contract, application produces the contract-prescribed visible evolution state transition; for every plan rejected by a structural contract rule, no evolution-state mutation occurs; and temporal staleness is handled per request as specified rather than invalidating unrelated requests.

The claim deliberately speaks in semantic terms rather than implementation terms. It does not name Rust functions, data structures, enum variants, or particular test cases.

## Candidate Oracle

The oracle is an independent **state-transition relation** derived from the design-level contract:

1. Start from an abstract scheduler state `S` consisting of active processes, genealogy/life graph, ready-to-run population, generation, and audit history.
2. Apply the contract's abstract plan-validation rules to an abstract evolution plan `P`.
3. If a structural rule rejects `P`, the oracle requires the evolution state to remain observationally identical to `S` (apart from any mutation explicitly allowed by the contract's audit semantics).
4. If `P` is valid, the oracle computes the expected abstract transition: valid deaths become inactive/fossilized with the specified death metadata; valid births become active descendants with the specified parent/birth metadata and runnable membership; generation advances exactly as prescribed; and the corresponding application audit outcome is recorded.
5. If a referenced entity has become temporally stale between planning and application, the oracle applies the contract's per-request tolerance rule: stale requests are skipped without invalidating unrelated valid requests.

The oracle must be implemented independently of the production Rust implementation. In particular, it must not call `apply_evolution_plan`, reuse its validation predicates, inspect its internal control flow, or derive expected results from the implementation's own output.

## Independence test

Before G11.1 is frozen, the following must be demonstrated:

- C1 can be stated without naming implementation symbols.
- The oracle can be evaluated without executing production implementation code.
- Expected outcomes can be generated from the contract before observing the implementation's result.
- No G11 test is used as a source for defining the claim or oracle.
- No current implementation detail is promoted to semantic law merely because the current tests assert it.

## Deliberately unresolved

The following are **not yet frozen** and must not be guessed from the implementation:

- exact abstract state representation;
- exact audit-state allowance on structural rejection;
- complete positive-case partition;
- complete negative-case partition;
- machine-readable evidence format;
- failure/triage policy for an oracle-vs-implementation mismatch.

## Freeze condition

G11.1 may be marked **FROZEN** only after C1 and the independent oracle have been reviewed for semantic independence from the current implementation. Until then:

> **No G11 tests, no G11 production changes, and no G11 PASS decision.**
