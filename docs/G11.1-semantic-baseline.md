## Minimal Claim C1

> **For every evolution request admitted by the frozen design-level contract, the implementation preserves the contract's explicitly stated safety and atomicity properties; for requests made stale by intervening evolution, the implementation applies the contract's temporal-tolerance rule.**

The Claim is limited to properties explicitly stated by Contract v1.0:

- **Capability safety:** protected/immune processes cannot be admitted through the evolution capability boundary.
- **Structural atomicity:** structurally invalid evolution plans do not partially mutate evolution state.
- **Build-then-commit atomicity:** a failed build does not partially commit the resulting evolution.
- **Temporal tolerance:** a request that has become stale is handled individually and does not invalidate unrelated valid requests.

The Claim does not add implementation-specific semantics.

## Independent Oracle O1

O1 is a finite set of falsifiable contract predicates over observable pre/post state and outcome. Each predicate is derived from Contract v1.0 before the implementation result is inspected.

### O1-A — Capability safety

For an evolution request requiring the evolution capability, an ineligible process must not be admitted as an authorized evolution target. A case in which an `Immune` or `Protected` process is treated as eligible through the normal capability boundary is an Oracle failure.

### O1-B — Structural atomicity

For a structurally invalid plan, compare the observable evolution state immediately before and after application. The required result is **zero evolution-state mutation**. Any observable partial evolution-state mutation makes O1 fail.

### O1-C — Build-then-commit atomicity

For an otherwise admissible plan whose child construction/build fails, compare observable evolution state immediately before and after application. The required result is **no committed evolution mutation**. Contract v1.0 explicitly requires no committed deaths, children, generation advance, or LifeGraph mutation on build failure. Any such committed mutation makes O1 fail.

### O1-D — Temporal tolerance

For a request that was valid when planned but becomes stale because the referenced entity disappears before application, the observable result must be **individual tolerance**: the stale request is skipped according to the contract and unrelated valid requests remain eligible. Treating the stale request as a plan-wide failure, or thereby invalidating an unrelated valid request, makes O1 fail.

## Scope boundary for successful valid requests

O1 does not impose an additional exact success-state oracle beyond the four properties above. Contract v1.0 contains additional life-graph/genealogy invariants, but they are deliberately outside this Gate until separately selected as G11 claims with their own explicit cases and evidence.

No additional success semantics may be inferred from the implementation during G11 test design.

## Independence test — PASSED

- C1 is stated without production implementation symbols.
- Every included property has a direct source in frozen Contract v1.0.
- O1 can be evaluated without executing production implementation code.
- Expected outcomes are determined from the frozen contract before observing implementation results.
- Each included predicate has a finite observable failure condition.
- No G11 test is used as a source for defining C1 or O1.
- No implementation detail has been promoted to semantic law merely because current tests assert it.

## Explicit non-claims

This Gate does not currently establish:

- a complete abstract state-transition relation;
- exact generation semantics;
- exact genealogy semantics;
- exact runnable-queue semantics;
- exact fossil/death metadata semantics;
- exact audit-state semantics.

Those properties remain contract material but are outside G11.1's selected claim surface.
